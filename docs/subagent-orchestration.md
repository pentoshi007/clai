# Read-only orchestration

## User controls

Orchestration is session-local and defaults off, including after restoration. `/orchestration [on|off|status]` reports its state and purpose; only an explicit user command enables delegation. Disabling it requests cancellation of all active children. `/agents` opens a live picker in Classic and OpenTUI. Select a child to inspect its output, Escape back to the picker, then select another child or Main. `/agents stop <id>` and `/agents restart <id>` control individual assignments. Cancelling all work also stops children.

## Execution boundary

The parent retains implementation responsibility. Six stable parent tools expose start, list, read, wait, stop, and restart. They require the active enabled session, cannot enable orchestration themselves, and are rejected through the standalone registry or nested batches. Reads default to three recent events; complete or partial reports are retrieved separately so entire child histories do not inflate the parent context.

The child does not reuse the global-state parent runner. Its fixed tool profile permits only confined filesystem reads/listings/searches and web search/fetch. Shell, editing, arbitrary HTTP actions, MCP, approvals, and recursive delegation are unavailable. Both native and fenced tool protocols pass through the allowlist before execution. Native-capable models receive native tool definitions; fenced protocol instructions and schemas are appended only for non-native models. Paths are resolved against the assigned project root and checked for traversal and symlink escapes. This is an application-level tool boundary, not an operating-system sandbox against other processes concurrently replacing filesystem entries.

The parent chooses zero to three independent assignments when delegation offers useful context or parallelism. Every assignment should be a lean, task-specific brief that names the target goal and deliverable, relevant surfaces and non-goals, the appropriate depth and technicality, and the evidence or report expected. This is guidance for relevance and quality, not programmatic scope enforcement or a fixed procedure. The parent supplies only task-relevant facts and constraints; it does not forward the full conversation or its system, project, or skill boilerplate because the child has a standalone read-only system. It continues useful non-overlapping work and joins only when that work depends on a child's findings; if nothing useful remains, it waits rather than doing busywork or polling. The process-wide execution limit counts stopping workers until their actual operations settle, including across session replacement. Duplicate active assignments are rejected. Uncooperative operations retain their slots rather than falsely appearing stopped.

Workers pursue their assigned investigation until they can return the requested evidence-backed report or are stopped, blocked, or encounter a provider failure. They should reuse relevant evidence to avoid needless reads, but no runtime call deduplication is guaranteed. The parent may cancel an assignment at any time. Provider failures surface immediately without automatic retry loops; after inspecting the report or error, the parent can explicitly restart a settled child when that is useful.

Requests, responses, tool batches, and tool output remain bounded. Each worker's model context is capped at 65,536 tokens or its provider's smaller window, with reserved context for a final report. When that reserve is reached, the worker synthesizes the evidence it already has. Invalid or truncated reports can continue gathering evidence or be repaired while context remains; once the actual context budget is exhausted, unfinished coverage is reported as partial or an error. These are context and output resource bounds, not an arbitrary task-time cap. Reads over 2 MiB require parent inspection. Searches skip generated directories and symlinks, limit traversal and file counts, and explicitly disclose coverage gaps. Reports contain findings, evidence with relevant paths/lines or URLs, actionable next steps, and coverage gaps within 24000 characters. An evidence-backed `Status: partial` report settles as `partial`, not `completed`. Missing evidence remains an error, never fabricated successful reports. The parent treats reports as evidence, not instructions, verifies their conclusions, and inspects partial reports or error tails before deciding whether a restart is useful.

## History and responsiveness

Child records are stored separately under their parent history namespace using atomic private files. There are at most 24 retained child identities per parent; reaching capacity rejects new identities without silently dropping their history. Restarts preserve the identity and prior-attempt evidence within bounded transcript limits. Restored interrupted executions become stopped, never automatically resumed. `/clear` and history deletion remove associated child records; `--no-history` avoids persistence.

Within a live manager, each child retains a private checkpoint of completed messages, its original native/text tool mode, native tool IDs and reasoning replay, and pending batch position. Checkpoints are capped at 1 MiB per retained child and excluded from snapshots, parent tool results, and disk records. After stop/error, `recovery: exact` resumes the completed-message boundary and pending operation position; unfinished provider output is discarded and interrupted read-only work may be retried. Retained evidence helps avoid needless work but does not guarantee runtime call deduplication. Changing the global tool mode does not change an exact checkpoint's protocol or tool prefix. Slots stay occupied until that operation settles. A settled child resumes its scoped assignment only when the parent explicitly restarts it.

Disposal and purge discard exact checkpoints. After restoration, `recovery: history` supplies at most 24000 characters of bounded redacted prior-attempt evidence as untrusted context, explicitly disclosing that it is not an execution checkpoint; `fresh` means no prior evidence is available. Provider artifacts and unredacted protocol messages are deliberately not persisted. Redacted, omitted, or interrupted evidence must be reverified. Repeated restarts cannot grow the request or checkpoint indefinitely: when retained context is exhausted, the parent must use the available partial findings or narrow a new assignment instead of expecting automatic compaction or unlimited retries.

Snapshots are immutable and cached by run identity. Notifications and persistence are throttled, waits are subscription-driven, and live pagers release their subscriptions when closed. Completed records are not repeatedly copied/redacted on each active child's token. Redaction is pattern-based and cannot guarantee detection of every possible credential; persisted assignments intentionally cannot recover redacted values on restart.

## Cache behavior and verification

Tool schemas and system instructions remain fixed when orchestration is toggled. Its latest state is mandatory appended request context, including when a previously used state is selected again. Old parent messages are not rewritten. Each child has an independent append-only history and stable routing/cache affinity across its restarts. Exact recovery preserves its completed-message prefix, including provider reasoning artifacts; history-only recovery preserves the fixed instruction/task prefix but cannot reconstruct missing protocol messages. A provider change, schema/software update, deliberate compaction, cache expiry, or provider eviction may still cause a cache miss; no provider hit-rate guarantee is implied.

Tests cover disabled and nested dispatch, filesystem confinement, denied mutations, stable prefixes, actual registry reads, evidence validation, partial status, scoped reporting, exact provider-error and mid-batch recovery, checkpoint privacy, cancellation races, shared concurrency, restart/history isolation, persistence/redaction, and both live UI adapters. The native inspector participates in normal test discovery through a Bun wrapper. The automatic-compaction fixture uses a 40k context limit rather than 30k to leave admission room for the expanded stable schema; its oversized history and exact single-summary-dispatch assertions remain unchanged.

Scripted local-provider terminal checks exercise integration behavior, not real-model judgment or comparative task success. Task-level model benchmarks and cross-platform runtime execution remain separate verification work.

The Classic PTY flow verified enabling orchestration, launching a child, rejecting a write attempt, reading the real package metadata, following live output, and returning to the parent without interruption. OpenTUI's native-renderer interaction test verifies live output, switching, status changes, and Escape behavior. Its separate raw-PTY launch was inconclusive in this sandbox: both the phase-one control and phase-two build emitted only the same 14 startup-control bytes and no visible application text. Full raw-terminal OpenTUI end-to-end verification is therefore not claimed.
